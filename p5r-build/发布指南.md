# 打包和发布

本项目采用「Git 维护源码，本地打包，GitHub Release 提供成品下载」的方式。

## 一键发布（推荐）

准备好本次版本并提交源码后，在项目根目录执行：

```powershell
python .\p5r-build\scripts\release.py
```

命令会自动完成：校验文件 → 打包 ZIP → 从更新日志生成发布说明 → 推送当前提交 → 创建版本草稿并上传 ZIP 和校验文件 → 检查附件名称和大小 → 正式发布，并输出下载页面链接。
不需要手动复制说明、上传附件或创建标签。版本号读取自 `ModConfig.json`，标签使用 `v版本号`；带 `-beta.1` 等后缀的版本会标记为预发布。

### 首次设置（只做一次）

1. 安装 Python 3、Git 和 [GitHub CLI](https://cli.github.com/)，安装后重新打开终端。
2. 运行 `gh auth login --hostname github.com`，跟随提示完成登录；随后运行 `gh auth setup-git` 配置 Git 认证。
3. 在 GitHub 创建用于这个项目的空仓库。在项目根目录配置远程地址（替换用户名和仓库名）：

   ```powershell
   git remote add origin https://github.com/你的用户名/你的仓库名.git
   ```

   若已经有 `origin`，使用 `git remote -v` 检查，无需重复添加。
4. 将当前项目提交到本地 Git。可以用 GitHub Desktop 检查待提交文件并提交，也可以使用自己熟悉的 Git 工具。

### 每次更新

准备好成品、版本号和 `changelog/版本号.md` 中的本次说明，提交这些修改，再运行一键发布命令即可。命令自动推送，无需单独执行 push。
提交前确保只有希望公开维护的文件被纳入 Git。脚本要求工作区干净，不会代你提交未知文件，也不会强制推送。
打包使用本地已准备的 DLL 和名称表，不会重新编译或生成它们。

只想提前检查安装包和说明，可以执行：

```powershell
python .\p5r-build\scripts\release.py --check
```

`--check` 不需要 GitHub 登录，不推送或发布；它不验证远程权限与发布条件。

### 失败时怎么办

- 提示缺少 `gh`、未登录、没有提交或没有远程仓库：完成首次设置。
- 提示工作区有修改：先提交本次源码、版本号和更新日志。
- 推送失败：检查登录权限和远程分支，解决后重试；不会强制覆盖远程修改。
- 上传或发布阶段失败：打开 GitHub Releases 检查草稿，确认两个附件完整，补齐后可直接在网页发布。如果想重新执行命令，先删除该失败草稿；若同时留下同名标签，先检查其对应提交并处理该标签。
- 已存在同版本 Release 或标签：命令会停止，防止覆盖历史版本。已公开的更新应使用新版本号。

若发布命令返回失败但网页上已显示公开版本，可能是最后的状态查询遇到网络问题；先核对网页，不要重复创建。

以下是文件准备说明和手动发布备用步骤。仅本地打包只需 Python 3，无需额外安装 Python 库。

## 1. 准备要发布的 Mod

先在本地完成修改和游戏内确认，再将要发布的内容放入 `p5rpc.skillrename/`：

```text
p5rpc.skillrename/
├─ ModConfig.json
├─ README.md
├─ 技能名称对照表.md
├─ SkillRename.dll
├─ CriFs.V2.Hook.Interfaces.dll
└─ Data/NAME.TBL
```

改名规则统一维护在 `p5r-build/config/changes.json`，版本号维护在 ModConfig 的 `ModVersion`。
修改后先运行 `python p5r-build/scripts/build-mod.py`，自动生成名称表、对照表和 `temp/current/changes.json` 校验记录，再提交源码和对照表。
打包会核对配置哈希、版本和名称表哈希；配置已变化时必须重新构建，不要手工修改生成的校验记录。

在根目录 [changelog/](../changelog/README.md) 中新建本版本文件，例如 `changelog/0.4.5.md`：

```markdown
# 0.4.5

- 在这里填写本次实际修改的内容。
```

文件名和首行版本必须与 `ModVersion` 一致。历史版本各自保留，不合并、不删除。
打包时只读取当前版本文件，连同安装说明写入 `release-notes.md`；Release 页面不会包含其他版本内容。
缺少文件、版本标题不匹配或内容为空时，脚本会停止并提示补充。
完整历史在 `changelog/` 目录中查看；发布脚本只读取日志，不修改它。
实际改动的文字需要维护者记录，脚本不会根据代码猜测更新内容。

打包脚本不会重新编译加载器，也不会生成名称表；它打包的是此目录中已准备好的成品。
已有构建方式见 [开发说明](readme.md)。从 GitHub 新下载的源码不含 DLL、游戏资源和下载依赖，需要先在本地准备这些材料。
只改名称时可以沿用加载器；修改加载器源码后，需要先重新编译并将新的 DLL 放入 Mod 目录。

## 2. 一条命令打包

在项目根目录打开终端，执行：

```powershell
python .\p5r-build\scripts\package-release.py
```

脚本会检查文件是否齐全、版本号是否一致、名称表是否匹配记录，然后校验 ZIP 内容。
这些检查不替代游戏内验证，也不证明 DLL 与最新源码一致。

以 0.4.4 为例，输出位置为：

```text
p5r-build/dist/v0.4.4/
├─ p5rpc.skillrename-v0.4.4.zip   上传给玩家的完整安装包
├─ SHA256SUMS.txt               安装包校验文件
└─ release-notes.md             可复制到 GitHub 的发布说明
```

安装包内有一个 `p5rpc.skillrename/` 文件夹，包含两份 DLL、名称表、Mod 配置、README 和最终名称对照表。
源码、下载材料、备份和历史版本不会打进去。`temp/current/changes.json` 仅用于打包校验，不放入安装包。
同一版本重复打包会更新本地输出；已公开发布后有新改动，应使用新版本号。

## 3. 将源码同步到 GitHub

先在 GitHub 建立仓库，将本地项目关联到它，然后提交并推送本次修改。
首次上传可以使用 GitHub Desktop 的添加本地仓库和发布仓库功能。
以后每次发布前，先提交、推送对应源码，确保发布版本有可追溯的记录。

本地 DLL、游戏名称表和 `dist/` 已被忽略，保留在你的电脑上；它们通过 Release 附件分发。

## 4. 在 GitHub 手动发布（备用）

1. 打开仓库页面，进入 **Releases**，点击 **Draft a new release**（首次可能显示 **Create a new release**）。
2. 新建标签，例如 `v0.4.4`；选择刚刚推送本次源码的分支或对应提交。标签是这个版本的源码记录，应与包内版本一致。
3. 标题填写「技能去异味 v0.4.4」。
4. 将自动生成的 `release-notes.md` 内容复制到发布说明，其中已包含当前版本的更新日志。
5. 在附件区上传 `p5rpc.skillrename-v0.4.4.zip` 和 `SHA256SUMS.txt`。不要只上传源码包。
6. 可先保存草稿检查，确认版本、说明和附件正确后点击 **Publish release**。

GitHub 自动附带的 **Source code (zip/tar.gz)** 仅包含仓库源码。玩家应下载你上传的 Mod ZIP。

使用一键发布时，准备并提交后只需运行 `release.py`，无需执行本节的网页操作。

目前采用本地打包，是因为构建依赖本机游戏资源和第三方材料；GitHub Actions 无法仅凭仓库源码直接生成完整成品。

参考：[GitHub 官方发布指南](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)。

一键发布使用 [GitHub CLI release create](https://cli.github.com/manual/gh_release_create) 和 [release edit](https://cli.github.com/manual/gh_release_edit)。
